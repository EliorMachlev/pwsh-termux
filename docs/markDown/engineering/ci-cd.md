# CI / CD

Workflows are in [`.github/workflows/`](../../../.github/workflows). They share these rules:

- **Every action is pinned to a commit SHA** with its version in a trailing comment (`uses: actions/checkout@<sha> # v7.0.1`). Tags can be moved; SHAs cannot. Dependabot proposes updates to both.
- **Least privilege.** `permissions: contents: read` at the top of each workflow; a job asks for more only where it needs it (`security-events: write` for code scanning, `pages: write` + `id-token: write` to deploy, `contents: write` to create release assets, `issues: write` for the staleness, key-review, audit and security.txt-renewal issues, `actions: write` only on the small keep-alive jobs that renew the scheduled workflows, `statuses: write` only on the job that pushes the [keep-alive commit](#keep-alive-commit)).
- **`step-security/harden-runner` first in every job**, in `audit` mode (it records the runner's network use).
- **`persist-credentials: false`** on every checkout, so the token is not left in `.git/config`. The one job that pushes ([keep-alive commit](#keep-alive-commit)) does not use the checkout's credentials either: its deploy key lives in an `ssh-agent` for the length of one script.
- **Concurrency.** A newer push to a pull request or topic branch cancels a run still going; runs on `main` always finish. Deploys share a `pages` group and are never cancelled.
- **Timeouts** on every job.
- **No `pull_request_target`**, and untrusted event data is never interpolated into a script.

## Schedule keep-alive

In a public repository GitHub disables every scheduled workflow after 60 days without repository activity. For most schedules here that only delays a scan, but `update.yaml` must re-sign the index at least every 14 days (`Valid-Until`), so a disabled schedule becomes an *expired* error on every device two weeks later. Two mechanisms work against it: the API renewal below, which makes no commit, and, because GitHub does not document that the renewal counts, a [keep-alive commit](#keep-alive-commit) on `main` after 30 quiet days, which is the documented kind of activity.

**What runs.** [`keep-schedules-alive.sh refresh`](../../../scripts/keep-schedules-alive.sh) finds every file in `.github/workflows` with a `schedule:` trigger, reads its state from the REST API and calls `PUT /repos/{owner}/{repo}/actions/workflows/{file}/enable` on each one that is `active` (renewing it before GitHub would disable it) or `disabled_inactivity` (bringing it back; the run then fails, so the maintainer hears of it). A workflow that is `disabled_manually` is left off: the [key recovery](release.md#recovery-with-the-offline-key) turns `update.yaml` off by hand on purpose. It runs in three places, each a small job with only `actions: write` (and `contents: read` for the checkout), no secret and no other step:

| Where | When |
|---|---|
| `update.yaml`, job `keepalive` | daily at 04:23 UTC, and on each push that deploys; independent of the build, so it runs when the build fails |
| `staleness.yaml`, job `keepalive` | daily at 07:41 UTC, after the `check` job has recorded the states (it runs whether that job passed or not) |
| `keepalive.yaml`, job `refresh` | Sundays and Wednesdays at 02:29 UTC; nothing else in it can fail |

Each run renews all the scheduled workflows, the other two legs and itself included, so a broken or deleted leg does not stop the others, and any one of them still running brings back the others if GitHub disables them one by one. `staleness.yaml`'s `check` job (with `actions: read`) opens the *A scheduled workflow is disabled* issue if it finds a `disabled_inactivity` state, before its own keep-alive job enables it again. Dry run: `GH_REPO=EliorMachlev/pwsh-termux bash scripts/keep-schedules-alive.sh refresh --dry-run` (or `check`) with a token that can read Actions, such as `gh auth`'s.

**Why this design.** A personal access token or a GitHub App key would be a new long-lived secret; a daily heartbeat commit would fill the history (the [keep-alive commit](#keep-alive-commit) is at most one a month, and only when nothing else was merged); a monthly issue is noise and its effect on the timer is undocumented. One dedicated workflow would be a single point of failure, and an enable call from a workflow that is already disabled cannot happen (a disabled workflow does not run), so the legs renew each other *before* the limit, daily, rather than wait to repair afterwards.

**Verified and assumed** (checked on 2026-11-12):

- *Documented:* scheduled workflows in a public repository are disabled automatically "when no repository activity has occurred in 60 days" ([events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule); [disabling and enabling a workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows)). A workflow's `state` is one of `active`, `deleted`, `disabled_fork`, `disabled_inactivity`, `disabled_manually`, and the enable endpoint sets it to `active` ([REST: workflows](https://docs.github.com/en/rest/actions/workflows)). Enable needs the *Actions* repository permission with write access ([permissions for GitHub Apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps)); `GITHUB_TOKEN` is a GitHub App installation token whose permissions the `permissions:` key sets ([GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token)). A commit that changes the `cron` of a deactivated scheduled workflow reactivates it.
- *Tested in this repository:* a job's `GITHUB_TOKEN` with `actions: write` calls the enable endpoint on an active workflow and gets `204 No Content` (the state stays `active`); with `actions: read` it gets `403 Resource not accessible by integration` but can read the state. `test-keepalive.sh` tests the script's own logic offline.
- *Not documented, assumed:* what counts as "repository activity". GitHub does not say. That scheduled runs alone do not count follows from the rule existing at all. That an enable call on an active workflow restarts its 60-day count is what the community keep-alive actions rely on (for example [`liskin/gh-workflow-keepalive`](https://github.com/liskin/gh-workflow-keepalive)), not something GitHub documents; it cannot be tested short of 60 days without a commit. Whether GitHub disables all of a repository's schedules at the same moment or each at its next run is not documented either; that GitHub emails before or when it disables them is reported by users, not documented.

**If the assumption is wrong**, the [keep-alive commit](#keep-alive-commit) still lands between day 30 and 37 of a quiet spell (its rulesets are in place and it has been verified end to end). If it fails too, the schedules can all stop together on day 60 and nothing inside the repository can restart them. What is left then: `staleness.yaml` prints the age of the last commit on `main` every day (and says so from day 45), so the risk is visible in its runs; a merged pull request (Dependabot opens grouped ones weekly) is a commit on `main` and resets the count; the maintainer can re-enable the workflows in the Actions tab or with `gh workflow enable`, then run `update.yaml` by hand. The index gives 14 more days before users see an error.

## Keep-alive commit

GitHub documents only commits on the default branch as repository activity. [`keepalive-commit.yaml`](../../../.github/workflows/keepalive-commit.yaml) runs [`keepalive-commit.sh`](../../../scripts/keepalive-commit.sh) every Monday: if `main`'s newest commit is younger than 30 days (`KEEPALIVE_MIN_AGE_DAYS`) it does nothing, since that commit already counts; otherwise it pushes one commit. So the history gets at most one such commit a month, and none while pull requests are being merged.

**`keep.alive`** is a file at the root of the repository that only this workflow writes. It holds one line, the UTC time of the last keep-alive commit (`2026-11-12T16:00:00Z`: exactly `KEEPALIVE_TIMESTAMP_REGEX` in [`scripts/lib/common.sh`](../../../scripts/lib/common.sh), 21 bytes with the newline). It has no other meaning; nothing reads it. The first run creates it. Do not edit it by hand or in a pull request: a change by anyone else is just a normal signed commit, but it is pointless.

**The commit.** Built with git plumbing in a temporary repository, on `main`'s tip fetched at depth 1: the tip's tree with `keep.alive` set, author and committer `github-actions[bot] <41898282+github-actions[bot]@users.noreply.github.com>`, message `chore(keepalive): refresh keep.alive [skip ci]` (so no push-triggered workflow runs for it). It is not signed: it is pushed with a deploy key that `main`'s ruleset lets bypass its rules.

**The guard**, before every push (and the same rules in the audit, `keepalive_commit_problems` in `common.sh`): exactly one parent, and it is the tip just fetched; exactly one changed path, `keep.alive`, added or modified, a regular file (mode `100644`, not a link); its content is one timestamp line that is also a real date; author and committer exactly the bot identity; the message exactly as above. The path check compares the raw NUL-separated list (`git diff -z --name-only`) with `keep.alive` and one NUL, byte for byte (`is_keepalive_path_list`), so a second file named `keep.alive<newline>` or `<newline>` cannot pass for nothing; the guard also runs it on the diff from the fetched tip itself. Anything else and nothing is pushed.

**The push** is `git push <remote> <commit>:refs/heads/main` over SSH, to `git@github.com`, with GitHub's Ed25519 host key pinned in the script (no other host key is accepted). If the push is refused and `main` has moved meanwhile, the script fetches again and starts over (the new tip may be young, which ends the run), at most 3 times; if it is refused and `main` has not moved, it fails at once: that is a rule, not a race. After the push it posts the commit status `keepalive/pushed` (`success`) on the new commit with the job's `GITHUB_TOKEN` (`statuses: write`); the audit requires it. If that call fails, the job fails and the next audit flags the commit.

**The key.** `KEEPALIVE_DEPLOY_KEY` is the private half of a read-write deploy key, a secret of the environment `keepalive`, whose deployment branch policy allows only `main`: a workflow run from any other branch, a pull request or a fork cannot read it. The job also refuses any ref but `refs/heads/main` itself, before the checkout, and the script does again. The script pipes the key into an `ssh-agent` (`ssh-add -`, a 15-minute lifetime), removes it from its environment, and kills the agent on exit: it is never written to disk, never echoed, and the checkout keeps `persist-credentials: false`. (actions/checkout's `ssh-key` input would write it to a file and, to push later, leave it configured, which is what zizmor's `artipacked` audit warns about; the agent avoids both.) Nothing else in the job can run code: harden-runner, a shell check of the ref, the pinned checkout, and the script.

**Why a deploy key.** `main`'s ruleset requires signed commits, a successful `github-pages` deployment and clean code scanning. In a personal repository GitHub Actions (`GITHUB_TOKEN`) cannot be a ruleset bypass actor, and a commit made by the workflow cannot be signed as anything GitHub verifies without a key of a user account or a GitHub App, which would be a broader credential. A deploy key can be a bypass actor (`actor_type: DeployKey`), has access to this repository only, and can do nothing but Git over SSH: no API, no issues, no settings, no secrets.

**What the key can do**, if it leaked: push any fast-forward commit to `main`, past the signature, deployment and code-scanning rules, including a change to a workflow, which then runs with whatever that workflow asks for, secrets included. That is why the rulesets ([release](release.md#rulesets)) keep deletion, non-fast-forward and creation in *Protection*, which the deploy key cannot bypass, and why every commit on `main` is [audited](#the-audit-of-main). So it cannot delete or rewrite `main` or create branches, and on existing branches other than `main` it is held to the rules of *Protection, other branches* (signed commits among them). It could create a tag on an existing signed commit: *Tag Protection* has `deletion`, `non_fast_forward`, `update` and `required_signatures` (plus a `required_status_checks` rule that lists no check), but no `creation` rule ([release](release.md#rulesets)).

**One deploy key only.** A ruleset bypass for deploy keys has no key id (`actor_id` is `null`): it applies to *every* deploy key of the repository. Never add a second one, read-only or not, for anything: it would be able to push to `main` too. `gh api repos/EliorMachlev/pwsh-termux/keys` must list exactly one key.

## The audit of main

[`audit-main.yaml`](../../../.github/workflows/audit-main.yaml) runs [`audit-main-commits.sh`](../../../scripts/audit-main-commits.sh) on each push to `main`, daily and by hand. It checks, newest first, every commit after a baseline (`AUDIT_BASELINE_COMMIT`, the last commit made before the ruleset required signatures) that was committed in the last 90 days (`AUDIT_WINDOW_DAYS`), the newest 50 (`AUDIT_MIN_COMMITS`) whatever their dates, so a back-dated commit is still seen, and on a push the pushed range. A commit is fine if:

- GitHub reports its signature verified and its committer's account is the repository's owner; or
- GitHub reports its signature verified, its committer's account is `web-flow`, **and** it is the merge commit of a merged pull request into `main`: `GET /repos/{owner}/{repo}/commits/{sha}/pulls` lists a pull request with `merged_at` set, base `main` and `merge_commit_sha` equal to the commit (the audit job has `pull-requests: read` for this). `web-flow` also signs commits made in github.com's editor and the earlier commits of a rebase merge, which are not any pull request's merge commit: those are findings. So merge pull requests with *Squash and merge* or a merge commit: a rebase merge of more than one commit flags every commit but its last, and so would any `web-flow`-signed commit a merge commit brings in; or
- it is unsigned and passes the [guard](#keep-alive-commit) above, and GitHub holds the status `keepalive/pushed` with state `success` on it, created by `github-actions[bot]` (login and account id 41898282). Only a workflow's `GITHUB_TOKEN` creates statuses as that account, and a deploy key cannot create a status at all, so a keep-alive-shaped commit pushed with a leaked key by hand is flagged.

If the audit job itself fails (an API error, a baseline missing from the clone, a rewritten `main`), it has checked nothing; the `failed` job (`contents: read`, `issues: write`, nothing else) then opens the issue *The audit of main failed*, or comments on it if it is open, and the next audit that runs to the end closes it.

Everything else is a finding: one issue, *Unexpected unsigned commit on main*, found by its exact title, opened with a table of the commits, their authors and the reasons; its body is replaced (with a comment) when the findings change and left alone when they do not; it is closed with a comment on the next clean run; the job fails while there are findings. A push that does not contain the previous tip (a rewritten `main`) is also a finding. After dealing with a finding (below), move `AUDIT_BASELINE_COMMIT` to the newest reviewed commit in a pull request, or the old commit keeps being flagged until it leaves the window.

**What it is and is not.** It is detection: tamper evidence after the fact, within a day (a push with `[skip ci]` in its message skips the push-triggered run, so the daily run is the bound). It is not prevention: whoever can push to `main` can also change this script and its workflow in the same push, and a verified signature only proves that the key belongs to the committer's account. Prevention is the main-only environment that holds the key, the ruleset that keeps deletion, force pushes and branch creation away from the deploy key, workflow changes reaching `main` only through signed, reviewed pull requests, and the single deploy key.

## Dependabot

[`dependabot.yml`](../../../.github/dependabot.yml) updates, weekly (Mondays): the pinned GitHub Actions, as one grouped pull request that moves both the SHA and its version comment, and the two hash-pinned Python requirement files (`.github/zizmor`, `.github/docs-checks`), as a second grouped pull request across both folders. Every update waits a 7-day cooldown after a release before it is proposed. Those are the only package ecosystems in the repository; the SBOM generators in `make-sboms.sh` are pinned by version and SHA-256 by hand. Every `uses:` is a full commit SHA with a `# vX.Y.Z` comment (local reusable workflows excepted), which is what lets Dependabot update them; Dependency Review and zizmor check each such pull request like any other.

## Secrets

Three: **`GPG_PRIVATE_KEY`**, the repository's signing key, and **`GPG_PASSPHRASE`**, its passphrase, both used only by `update.yaml`'s "Build the signed apt repository" step, in the `publish` job, which runs in the environment `signing`: both are secrets of that environment, whose deployment branch policy allows only `main`, and neither is a repository secret ([release](release.md#one-time-setup)). The step writes the passphrase to a mode-600 file under `RUNNER_TEMP`, passes it to `build-repo.sh` as `GPG_PASSPHRASE_FILE` (gpg reads it with `--pinentry-mode loopback --passphrase-file`, never from an argument), removes it when the step ends and again in an `always()` step, and unsets both secrets before `build-repo.sh` runs. Because the passphrase sits beside the key in the same environment, it protects only against a leak of the key alone ([release](release.md#one-time-setup)). The third, **`KEEPALIVE_DEPLOY_KEY`**, is a secret of the environment `keepalive` (main only), used only by `keepalive-commit.yaml`'s push step ([security](security.md#secrets)). `GITHUB_TOKEN` is the workflows' own, scoped per job.

## When a run fails

- **`update.yaml` fails, the site stays as it was.** Nothing is deployed from a failed run.
- **"GPG_PRIVATE_KEY secret is not set"**: the secret is missing; [release](release.md#one-time-setup) says how to add it.
- **"gpg could not sign …"** from `build-repo.sh`: the key is passphrase-protected and `GPG_PASSPHRASE` is missing or wrong (or the key itself is unusable). A warning *GPG_PASSPHRASE secret is not set* means the run signed with a key that has no passphrase; that should not happen, since the key in `signing` is protected: check `gh secret list --env signing` lists `GPG_PASSPHRASE` ([release](release.md#one-time-setup)).
- **Checksum mismatch or "no checksum for …"**: Microsoft's `hashes.sha256` and the tarball disagree, or its format changed. Do not work around it; see [packaging](architecture/packaging.md).
- **`find-releases.sh` finds no stable release**: usually the GitHub API is down or rate limited; re-run.
- **An issue *The live apt index is stale or unreachable* is open**: `staleness.yaml` found fewer than 7 days left, an index that does not verify against `keys/`, or no index at all. Look at `update.yaml`'s recent runs first; the issue closes itself once the index is fresh again.
- **`pkg update` says the Release file *is expired***: `update.yaml` has not deployed for more than 14 days, so the index's `Valid-Until` has passed. Find the failing run and fix it, or re-run it; the next deploy fixes every device. During a recovery, the maintainer re-signs offline instead ([release](release.md#recovery-with-the-offline-key)).
- **"… is more than 14 days after Date", "expired at", "only N day(s) left"** from `build-repo.sh`, `recovery-sign.sh` or `verify-recovery-repo.sh`: the `Release` window is wrong or too old. For a recovery, run `build-repo.sh` again and sign in the same sitting.
- **A scheduled workflow stops running**, or an issue *A scheduled workflow is disabled* is open: GitHub disabled it for inactivity (60 days without repository activity) and the [keep-alive](#schedule-keep-alive) did not hold, or a keep-alive run failed with *GitHub had disabled … for inactivity*. Re-enable every scheduled workflow (`gh workflow enable <file>`, or the Actions tab), run `update.yaml` by hand if it was among them (the index expires 14 days after its last re-sign), and merge something to `main` if it keeps happening. *could not enable … (does the job have actions: write?)*: the job's `permissions:` lost `actions: write`.
- **An issue *The audit of main failed* is open**: `audit-main.yaml`'s audit job failed, so nothing was checked. Read the linked run. An API error: run *Audit main* again. *the baseline … is not an ancestor of HEAD*: `main` was rewritten; treat it like a finding (next item). *could not read the pull requests of …*: the job's `permissions:` lost `pull-requests: read`, or the API failed.
- **An issue *Unexpected unsigned commit on main* is open**: a commit on `main` is neither signed by a trusted account nor a keep-alive commit with its status. Treat it as a possible leak of the keep-alive deploy key: rotate the key ([release](release.md#rotating-the-keep-alive-deploy-key)), look at what the commits changed and revert what is not yours, check recent workflow runs, and rotate any secret a changed workflow could have read. A keep-alive commit flagged only for its missing status, after a keep-alive run that failed while posting it, is the harmless case: the run's log says so.
- **`keepalive-commit.yaml` fails with *the push was refused and main has not moved***: the ruleset does not let the deploy key push to `main` (not set up yet, or the bypass was removed), or the key was rotated without updating the secret. *ssh-add refused KEEPALIVE_DEPLOY_KEY*: the secret is not an OpenSSH private key. *KEEPALIVE_DEPLOY_KEY is not set*: the job did not run in the `keepalive` environment, or the secret is missing.
