# CI / CD

Workflows are in [`.github/workflows/`](../../../.github/workflows). They share these rules:

- **Every action is pinned to a commit SHA** with its version in a trailing comment (`uses: actions/checkout@<sha> # v7.0.1`). Tags can be moved; SHAs cannot. Dependabot proposes updates to both.
- **Least privilege.** `permissions: contents: read` at the top of each workflow; a job asks for more only where it needs it (`security-events: write` for code scanning, `pages: write` + `id-token: write` to deploy, `contents: write` to create release assets, `issues: write` for the staleness and key-review issues).
- **`step-security/harden-runner` first in every job**, in `audit` mode (it records the runner's network use).
- **`persist-credentials: false`** on every checkout, so the token is not left in `.git/config`.
- **Concurrency.** A newer push to a pull request or topic branch cancels a run still going; runs on `main` always finish. Deploys share a `pages` group and are never cancelled.
- **Timeouts** on every job.
- **No `pull_request_target`**, and untrusted event data is never interpolated into a script.

## Workflows

| Workflow | What it does |
|---|---|
| [`build-packages.yaml`](../../../.github/workflows/build-packages.yaml) | **Build, SBOMs and provenance** (reusable, called by `update.yaml`). Finds releases, builds the `.deb` files (`pwsh`, `pwsh-preview`, and `pwsh-termux-keyring` from `keys/` with `build-keyring.sh`), writes four SBOMs per package, attests the lot. No signing key. |
| [`update.yaml`](../../../.github/workflows/update.yaml) | **The pipeline.** Calls `build-packages.yaml`; a `verify` job (read-only token, no signing key) checks the keyring package's provenance with `scripts/verify-attestation.sh`; `publish` builds and signs the repository (refusing a signing key that is not the key in `keys/`, and a keyring package that is not the verified file or does not ship `keys/`), merges the website, archives each new `pwsh`/`pwsh-preview` `.deb` with its SBOMs, provenance, the public key and the keyring package as a release, deploys to Pages. Releases are created once and never modified, so [immutable releases](release.md#one-time-setup) can be on. Daily (release or not: each run re-signs the index, whose `Valid-Until` is 14 days ahead, without a commit), on pushes to `scripts/**`, `keys/**`, `docs/**`, `build-packages.yaml` and itself, and by hand. Refuses to run without `GPG_PRIVATE_KEY`. |
| [`ci.yaml`](../../../.github/workflows/ci.yaml) | `shellcheck` on `scripts/*.sh` and `scripts/lib/*.sh`; `actionlint` (a release binary checked against a pinned SHA-256 before it runs); **keys**: `check-keys.sh` on `keys/` (one online key, plus the keys `keys/RECOVERY` and `keys/ROTATION` name), SECURITY.md lists the current and the recovery fingerprint, and `test-keys.sh` (throwaway keys and a stub `gh`: the shapes `{online}`, `{online, recovery}`, `{online, next}`, `{online, next, recovery}` accepted; a stray key, a stale or wrong marker, a wrong signer, the recovery key as signer or its secret in the CI gpg home, an altered, unverified or unattested keyring package refused; recovery signing and its verification, including tampered recovery repositories; `Valid-Until`: present, an RFC 1123 date, exactly 14 days after `Date`, in the signed text; two builds of the same packages at different times give byte-identical `Packages*` and `.deb` files while `Release`, `InRelease` and `Release.gpg` differ; a recovery index with no, an unbounded, an expired, a nearly expired (under 7 days), a future-dated or a malformed window refused; `check-index-freshness.sh` accepting a fresh index signed by the online or the recovery key and refusing a stale, expired, unbounded, wrongly signed or error-page one); a **package build** of the current stable release, built twice and compared byte for byte (a daily rebuild must not change `Packages`), with checks of the patched loader and the symlink, the keyring package built twice and compared byte for byte (a reproducibility test) and checked to ship `keys/` and the `signed-by` source, the SBOMs of both, an unsigned repository and the site assembly, then a repository signed with a throwaway key through the test-only `KEYRING_FILE`. |
| [`recover.yaml`](../../../.github/workflows/recover.yaml) | **Only after a lost or compromised online key**, started by hand with a `recovery-*` release tag. Deploys a repository the maintainer signed offline with the recovery key, after `verify-recovery-repo.sh` checks it against the recovery key alone; holds no signing key; key files and site come from the commit ([release](release.md#recovery-with-the-offline-key)). |
| [`staleness.yaml`](../../../.github/workflows/staleness.yaml) | **Daily** (and by hand): fetches the live `https://pwsh-termux.machlev.org/dists/stable/InRelease`, verifies it against `keys/` and checks that at least 7 days are left before `Valid-Until` ([`check-index-freshness.sh`](../../../scripts/check-index-freshness.sh)). If not, or if it cannot be fetched, it opens an issue titled *The live apt index is stale or unreachable*, or comments on the open one (never a second), and fails; when the index is healthy again it closes the issue. `issues: write` only. |
| [`key-review.yaml`](../../../.github/workflows/key-review.yaml) | Every 2 January (and by hand): opens a *Yearly key review* issue, a checklist for the offline recovery-key backup, the revocation certificates, the fingerprints and the rotation plan. No key material; one issue per year. `issues: write` only. |
| [`site.yaml`](../../../.github/workflows/site.yaml) | [`site-check.py`](../../../.github/scripts/site-check.py): CSP, no scripts, nothing from another site, local links, sitemap, robots, `security.txt`, `CNAME` ([website](website.md)). |
| [`renew-security-txt.yaml`](../../../.github/workflows/renew-security-txt.yaml) | On the 1st of each month, moves `security.txt`'s `Expires` to about eleven months ahead if fewer than four are left, commits it to `main` and starts `update.yaml` to deploy it. |
| [`docs-checks.yaml`](../../../.github/workflows/docs-checks.yaml) | **lychee** (a pinned, checksum-verified release) checks every local link and `#anchor` in the Markdown and pages on each change, and external links weekly; **typos** (hash-pinned) checks spelling. |
| [`zizmor.yaml`](../../../.github/workflows/zizmor.yaml) | Audits the workflows for template injection, over-broad permissions, leftover credentials, unpinned or impostor actions. Every finding goes to code scanning; medium or higher fails the job. zizmor is installed from `.github/zizmor/requirements.txt` with `--require-hashes`. |
| [`codeql.yaml`](../../../.github/workflows/codeql.yaml) | CodeQL for the `actions` language (there is no CodeQL pack for shell). |
| [`gitleaks.yaml`](../../../.github/workflows/gitleaks.yaml) | Scans the whole history for secrets, built from a pinned commit (checked after fetching) and cached. Matches are redacted in the log. |
| [`dependency-review.yaml`](../../../.github/workflows/dependency-review.yaml) | On pull requests, fails on a new dependency with a high-severity advisory. |
| [`scorecard.yaml`](../../../.github/workflows/scorecard.yaml) | OpenSSF Scorecard, published weekly and on pushes; the README badge reads it. |

## Dependabot

[`dependabot.yml`](../../../.github/dependabot.yml) updates, weekly (Mondays): the pinned GitHub Actions, as one grouped pull request that moves both the SHA and its version comment, and the two hash-pinned Python requirement files (`.github/zizmor`, `.github/docs-checks`), as a second grouped pull request across both folders. Every update waits a 7-day cooldown after a release before it is proposed. Those are the only package ecosystems in the repository; the SBOM generators in `make-sboms.sh` are pinned by version and SHA-256 by hand. Every `uses:` is a full commit SHA with a `# vX.Y.Z` comment (local reusable workflows excepted), which is what lets Dependabot update them; Dependency Review and zizmor check each such pull request like any other.

## Secrets

One: **`GPG_PRIVATE_KEY`**, the repository's signing key, used only by `update.yaml`'s "Build the signed apt repository" step ([security](security.md#secrets)). `GITHUB_TOKEN` is the workflows' own, scoped per job.

## When a run fails

- **`update.yaml` fails, the site stays as it was.** Nothing is deployed from a failed run.
- **"GPG_PRIVATE_KEY secret is not set"**: the secret is missing; [release](release.md#one-time-setup) says how to add it.
- **Checksum mismatch or "no checksum for …"**: Microsoft's `hashes.sha256` and the tarball disagree, or its format changed. Do not work around it; see [packaging](architecture/packaging.md).
- **`find-releases.sh` finds no stable release**: usually the GitHub API is down or rate limited; re-run.
- **An issue *The live apt index is stale or unreachable* is open**: `staleness.yaml` found fewer than 7 days left, an index that does not verify against `keys/`, or no index at all. Look at `update.yaml`'s recent runs first; the issue closes itself once the index is fresh again.
- **`pkg update` says the Release file *is expired***: `update.yaml` has not deployed for more than 14 days, so the index's `Valid-Until` has passed. Find the failing run and fix it, or re-run it; the next deploy fixes every device. During a recovery, the maintainer re-signs offline instead ([release](release.md#recovery-with-the-offline-key)).
- **"… is more than 14 days after Date", "expired at", "only N day(s) left"** from `build-repo.sh`, `recovery-sign.sh` or `verify-recovery-repo.sh`: the `Release` window is wrong or too old. For a recovery, run `build-repo.sh` again and sign in the same sitting.
- **A scheduled workflow stops running**: GitHub disables schedules after 60 days without repository activity; re-enable it in the Actions tab or push a commit. For `update.yaml` this matters within 14 days: without the daily re-sign the index expires. `staleness.yaml` is a schedule too, so it stops with it; GitHub emails the maintainer before it disables them.
