# CI / CD

Workflows are in [`.github/workflows/`](../../../.github/workflows). They share these rules:

- **Every action is pinned to a commit SHA** with its version in a trailing comment (`uses: actions/checkout@<sha> # v7.0.1`). Tags can be moved; SHAs cannot. Dependabot proposes updates to both.
- **Least privilege.** `permissions: contents: read` at the top of each workflow; a job asks for more only where it needs it (`security-events: write` for code scanning, `pages: write` + `id-token: write` to deploy, `contents: write` to create release assets, `issues: write` for the staleness and key-review issues, `actions: write` only on the small keep-alive jobs that renew the scheduled workflows).
- **`step-security/harden-runner` first in every job**, in `audit` mode (it records the runner's network use).
- **`persist-credentials: false`** on every checkout, so the token is not left in `.git/config`.
- **Concurrency.** A newer push to a pull request or topic branch cancels a run still going; runs on `main` always finish. Deploys share a `pages` group and are never cancelled.
- **Timeouts** on every job.
- **No `pull_request_target`**, and untrusted event data is never interpolated into a script.

## Schedule keep-alive

In a public repository GitHub disables every scheduled workflow after 60 days without repository activity. For most schedules here that only delays a scan, but `update.yaml` must re-sign the index at least every 14 days (`Valid-Until`), so a disabled schedule becomes an *expired* error on every device two weeks later. A commit on `main` is not something to fake: the ruleset requires signed commits and a Pages deployment, and a commit a day (or month) would only be noise in the history.

**What runs.** [`keep-schedules-alive.sh refresh`](../../../scripts/keep-schedules-alive.sh) finds every file in `.github/workflows` with a `schedule:` trigger, reads its state from the REST API and calls `PUT /repos/{owner}/{repo}/actions/workflows/{file}/enable` on each one that is `active` (renewing it before GitHub would disable it) or `disabled_inactivity` (bringing it back; the run then fails, so the maintainer hears of it). A workflow that is `disabled_manually` is left off: the [key recovery](release.md#recovery-with-the-offline-key) turns `update.yaml` off by hand on purpose. It runs in three places, each a small job with only `actions: write` (and `contents: read` for the checkout), no secret and no other step:

| Where | When |
|---|---|
| `update.yaml`, job `keepalive` | daily at 04:23 UTC, and on each push that deploys; independent of the build, so it runs when the build fails |
| `staleness.yaml`, job `keepalive` | daily at 07:41 UTC, after the `check` job has recorded the states (it runs whether that job passed or not) |
| `keepalive.yaml`, job `refresh` | Sundays and Wednesdays at 02:29 UTC; nothing else in it can fail |

Each run renews all the scheduled workflows, the other two legs and itself included, so a broken or deleted leg does not stop the others, and any one of them still running brings back the others if GitHub disables them one by one. `staleness.yaml`'s `check` job (with `actions: read`) opens the *A scheduled workflow is disabled* issue if it finds a `disabled_inactivity` state, before its own keep-alive job enables it again. Dry run: `GH_REPO=EliorMachlev/pwsh-termux bash scripts/keep-schedules-alive.sh refresh --dry-run` (or `check`) with a token that can read Actions, such as `gh auth`'s.

**Why this design.** A personal access token or a GitHub App key would be a new long-lived secret; a heartbeat commit would be unsigned (or need write access to `main` and a deployment) and would fill the history; a monthly issue is noise and its effect on the timer is undocumented. One dedicated workflow would be a single point of failure, and an enable call from a workflow that is already disabled cannot happen (a disabled workflow does not run), so the legs renew each other *before* the limit, daily, rather than wait to repair afterwards.

**Verified and assumed** (checked on 2026-11-12):

- *Documented:* scheduled workflows in a public repository are disabled automatically "when no repository activity has occurred in 60 days" ([events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule); [disabling and enabling a workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows)). A workflow's `state` is one of `active`, `deleted`, `disabled_fork`, `disabled_inactivity`, `disabled_manually`, and the enable endpoint sets it to `active` ([REST: workflows](https://docs.github.com/en/rest/actions/workflows)). Enable needs the *Actions* repository permission with write access ([permissions for GitHub Apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps)); `GITHUB_TOKEN` is a GitHub App installation token whose permissions the `permissions:` key sets ([GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token)). A commit that changes the `cron` of a deactivated scheduled workflow reactivates it.
- *Tested in this repository:* a job's `GITHUB_TOKEN` with `actions: write` calls the enable endpoint on an active workflow and gets `204 No Content` (the state stays `active`); with `actions: read` it gets `403 Resource not accessible by integration` but can read the state. `test-keepalive.sh` tests the script's own logic offline.
- *Not documented, assumed:* what counts as "repository activity". GitHub does not say. That scheduled runs alone do not count follows from the rule existing at all. That an enable call on an active workflow restarts its 60-day count is what the community keep-alive actions rely on (for example [`liskin/gh-workflow-keepalive`](https://github.com/liskin/gh-workflow-keepalive)), not something GitHub documents; it cannot be tested short of 60 days without a commit. Whether GitHub disables all of a repository's schedules at the same moment or each at its next run is not documented either; that GitHub emails before or when it disables them is reported by users, not documented.

**If the assumption is wrong**, the schedules can all stop together on day 60 and nothing inside the repository can restart them. What is left then: `staleness.yaml` prints the age of the last commit on `main` every day (and says so from day 45), so the risk is visible in its runs; a merged pull request (Dependabot opens grouped ones weekly) is a commit on `main` and resets the count; the maintainer can re-enable the workflows in the Actions tab or with `gh workflow enable`, then run `update.yaml` by hand. The index gives 14 more days before users see an error.

## Dependabot

[`dependabot.yml`](../../../.github/dependabot.yml) updates, weekly (Mondays): the pinned GitHub Actions, as one grouped pull request that moves both the SHA and its version comment, and the two hash-pinned Python requirement files (`.github/zizmor`, `.github/docs-checks`), as a second grouped pull request across both folders. Every update waits a 7-day cooldown after a release before it is proposed. Those are the only package ecosystems in the repository; the SBOM generators in `make-sboms.sh` are pinned by version and SHA-256 by hand. Every `uses:` is a full commit SHA with a `# vX.Y.Z` comment (local reusable workflows excepted), which is what lets Dependabot update them; Dependency Review and zizmor check each such pull request like any other.

## Secrets

One: **`GPG_PRIVATE_KEY`**, the repository's signing key, used only by `update.yaml`'s "Build the signed apt repository" step ([security](security.md#secrets)). `GITHUB_TOKEN` is the workflows' own, scoped per job.

## When a run fails

- **`update.yaml` fails, the site stays as it was.** Nothing is deployed from a failed run.
- **"GPG_PRIVATE_KEY secret is not set"**: the secret is missing; [release](release.md#one-time-setup) says how to add it.
- **Checksum mismatch or "no checksum for …"**: Microsoft's `hashes.sha256` and the tarball disagree, or its format changed. Do not work around it; see [packaging](architecture/packaging.md).
- **`find-releases.sh` finds no stable release**: usually the GitHub API is down or rate limited; re-run.
- **An issue *The live apt index is stale or unreachable* is open**: `staleness.yaml` found fewer than 7 days left, an index that does not verify against `keys/`, or no index at all. Look at `update.yaml`'s recent runs first; the issue closes itself once the index is fresh again.
- **`pkg update` says the Release file *is expired***: `update.yaml` has not deployed for more than 14 days, so the index's `Valid-Until` has passed. Find the failing run and fix it, or re-run it; the next deploy fixes every device. During a recovery, the maintainer re-signs offline instead ([release](release.md#recovery-with-the-offline-key)).
- **"… is more than 14 days after Date", "expired at", "only N day(s) left"** from `build-repo.sh`, `recovery-sign.sh` or `verify-recovery-repo.sh`: the `Release` window is wrong or too old. For a recovery, run `build-repo.sh` again and sign in the same sitting.
- **A scheduled workflow stops running**, or an issue *A scheduled workflow is disabled* is open: GitHub disabled it for inactivity (60 days without repository activity) and the [keep-alive](#schedule-keep-alive) did not hold, or a keep-alive run failed with *GitHub had disabled … for inactivity*. Re-enable every scheduled workflow (`gh workflow enable <file>`, or the Actions tab), run `update.yaml` by hand if it was among them (the index expires 14 days after its last re-sign), and merge something to `main` if it keeps happening. *could not enable … (does the job have actions: write?)*: the job's `permissions:` lost `actions: write`.
